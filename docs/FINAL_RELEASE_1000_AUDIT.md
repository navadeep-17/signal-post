## Release-verifier correction history

The first valid release workflow run (`35242975813`) completed the production runner successfully for all ten chunks, but a release-only assertion incorrectly required `len(claims) == len(evidence)`. That assumption conflicts with the output contract because evidence is deduplicated and may support multiple claims.

The manifest was not changed. Commit `550bba0cce64a0a26d878c3b7f41eb20a55dc10e` replaced that assertion with the repository's canonical `validate_contract_object()` validator, pinned the existing manifest SHA, and replayed the exact same 1,000 companies. Replay `35246833190` then passed all ten chunks and the aggregate.

## What this release audit establishes

It establishes that the current production stack can process a fresh, deterministic, zero-overlap 1,000-company sample as ten independent evaluator-shaped 100-company workloads while preserving:

- terminal completeness
- exact output-contract validity
- bounded request use
- bounded runtime
- $0 third-party API spend
- zero search-API dependence
- high official-source workforce availability
- evidence-backed external observations
- explicit abstention rather than unsupported inference
- snapshot-drift resilience

## What it does not establish

Builderr's official external company recall, claim recall, coverage/source-discovery score, and total challenge score use a hidden evaluator-owned availability denominator and external union. Therefore this audit **must not** be presented as proof that the >=60% weighted external-company-recall gate, >=21/35 coverage gate, or >=65 total-score threshold is already met.

The appropriate next phase is synthesis/UX hardening and submission packaging over this now-frozen, certified release behavior—not further broad connector hunting or tuning against the release corpus.
